# IPC contract

Every Tauri command returns `Promise<T>` or rejects with `AppError { kind, message }`
(`src/lib/ipc.ts`, `src-tauri/src/error.rs`). Argument names are camelCase on the TypeScript
side and Tauri maps them to snake_case Rust parameters automatically.

All JSON field names below are **camelCase**. Rust structs use `#[serde(rename_all = "camelCase")]`.
Enums use `#[serde(tag = "kind")]` or `#[serde(tag = "t")]` as shown.

## Connections

```ts
type ConnectionId = string // uuid v4, generated by backend when saving with id === ""

interface MysqlConnectionConfig {
  kind: "mysql"
  id: ConnectionId
  name: string
  host: string
  port: number           // 1..65535
  user: string
  database?: string      // default schema, optional
  color?: string         // optional accent, exactly "#rrggbb", e.g. "#7c9cff"
  tls?: MysqlTlsMode     // default "preferred"; omitted when not set
  caCertPath?: string    // absolute path to a PEM CA bundle; only with verify_ca / verify_identity
}

// preferred: TLS when the server offers it, certificate not verified (sqlx Preferred)
// required:  TLS or fail, certificate not verified
// verify_ca: TLS, certificate chain verified against caCertPath, or the bundled Mozilla roots
//            (webpki-roots) when caCertPath is absent. Known limitation: with sqlx 0.8.6 and
//            rustls 0.23.46 the host name is also checked (fails closed), so it currently
//            behaves like verify_identity.
// verify_identity: verify_ca plus the certificate must name `host`.
type MysqlTlsMode = "preferred" | "required" | "verify_ca" | "verify_identity"

interface DynamoConnectionConfig {
  kind: "dynamodb"
  id: ConnectionId
  name: string
  region: string         // e.g. "ap-northeast-2"
  endpoint?: string      // e.g. "http://localhost:8000" for DynamoDB Local
  auth:
    | { type: "profile"; profile: string }      // ~/.aws profile name, SSO supported
    | { type: "keys"; accessKeyId: string }     // secret access key lives in keyring
  color?: string
}

interface AthenaConnectionConfig {
  kind: "athena"
  id: ConnectionId
  name: string
  region: string         // e.g. "ap-northeast-2"
  auth: AwsAuth          // same union as DynamoDB (`profile` / `keys`); the secret key lives in the secret store
  workgroup?: string     // absent means "primary"
  outputLocation?: string // "s3://bucket[/prefix/]"; absent means the workgroup's, else the default bucket (see Athena)
  database?: string      // default database of new query tabs
  color?: string
}

type AwsAuth =
  | { type: "profile"; profile: string }
  | { type: "keys"; accessKeyId: string }

type ConnectionConfig = MysqlConnectionConfig | DynamoConnectionConfig | AthenaConnectionConfig
```

Secrets (MySQL password, AWS secret access key) are never part of `ConnectionConfig`. They are
passed only as the `secret` argument of `connections_save` / `connections_test` and stored in the
OS keyring under service `ratelquery`, account `<connection id>`.

Configs are persisted as JSON at `<app config dir>/connections.json` (Tauri `app_config_dir`),
written atomically (write temp file, rename) with owner-only permissions (`0600` on unix).

| command | args | returns |
| --- | --- | --- |
| `connections_list` | – | `ConnectionConfig[]` sorted by name |
| `connections_save` | `config: ConnectionConfig`, `secret: string \| null` | saved `ConnectionConfig` (with generated id). `secret === null` keeps the stored secret; `""` clears it. Keeping a stored secret (`null`) while the config no longer targets the saved server (same rule as `connections_test` below) rejects with `kind: "invalid_input"` ("Enter the password again for the new server" / "Enter the secret access key again for the new endpoint or key") and saves nothing. |
| `connections_delete` | `id` | `void`. Closes any open session (without waiting for running queries), then removes the secret from both secret stores and the config. Only the active store's failure counts: the config is still removed and the call rejects with `kind: "credential"` ("... its saved secret is still in the keychain ..." or "... still in secrets.json ..."); a failure of the inactive store is ignored. |
| `connections_has_secret` | `id` | `boolean` |
| `connections_duplicate` | `id` | the saved copy (`ConnectionConfig`): same settings under a new UUID id and the first free name of `"<name> copy"`, `"<name> copy 2"`, … (compared case-insensitively). The stored secrets (database and SSH) are copied inside the backend and never cross IPC. If a secret cannot be copied the copy is removed again, its copied secrets included, and the call rejects with that error (`kind: "credential"`); if removing the copy from `connections.json` fails as well, the copied secrets are still removed and that `kind: "io"` error is returned instead. Unknown `id` is `not_found`, an empty one `invalid_input`. |
| `connection_layout_load` | – | the saved sidebar layout (see below) or `null` when none was saved. A corrupt, oversized (over 1 MiB) or non-version-1 file is logged and also `null`; a file that exists but can't be read rejects with `kind: "io"`. The frontend validates the shape and treats anything else as `null`. |
| `connection_layout_save` | `layout: ConnectionLayout` | `void`. Replaces `connection-layout.json` atomically (owner-only permissions). Anything but a JSON object with `version: 1`, or an encoding over 1 MiB, rejects with `kind: "invalid_input"` and writes nothing. |
| `connections_test` | `config: ConnectionConfig`, `secret: string \| null` | `{ ok: true, serverVersion?: string, latencyMs: number, athena?: AthenaTestInfo }`. Rejects with `kind: "connection"` on failure. A `null` secret falls back to the stored one for `config.id` **only when the config still targets the saved server**: same host (case-insensitive), port, user, `tls` and `caCertPath` for MySQL; same endpoint, region and auth (`accessKeyId` / `profile`) for DynamoDB; same region and auth for Athena. Otherwise it rejects with `kind: "invalid_input"` ("Enter the password again to test a different server" / "Enter the secret access key again to test a different endpoint or key"); name, database, workgroup, output location and color changes do not matter. For Athena the probe is `GetWorkGroup` plus the output-location resolution below; `athena` is set only for Athena configs. |
| `aws_profiles` | – | `{ name: string, region: string \| null, source: "config" \| "credentials" \| "both", sso: boolean }[]` sorted by name: `[default]` / `[profile x]` of `AWS_CONFIG_FILE` (else `~/.aws/config`) merged with `[x]` of `AWS_SHARED_CREDENTIALS_FILE` (else `~/.aws/credentials`). `region` is the config section's `region` only (never an SSO session's `sso_region`); `sso` is true when the config section has `sso_start_url` or `sso_session`. Missing files give `[]`, unparsable lines are skipped, an unreadable file rejects with `kind: "io"`. No secret value is read into or returned in the result. |

Validation (backend, `kind: "invalid_input"`): name non-empty, host non-empty, port in range,
region non-empty, profile non-empty, accessKeyId non-empty, `color` is `#rrggbb`, `endpoint` is
an absolute `http://` or `https://` URL with a host and without user info (`user:pass@`) or a
`#` fragment, `caCertPath` is absolute and only set with `tls` `verify_ca` / `verify_identity`, `workgroup`
non-empty when present, `outputLocation` (when present) is `s3://<bucket>` or
`s3://<bucket>/<prefix>` with a bucket name of 3–63 lowercase letters, digits, dots or hyphens
(a missing trailing `/` is added). Text fields, `user` and `id` are trimmed. An empty `id`
passed to `connections_delete` or `connections_has_secret` is rejected.

The sidebar order and folders live in `<app config dir>/connection-layout.json`. The frontend owns
the shape; the backend only checks the version and size:

```ts
interface ConnectionLayout {
  version: 1
  folders: { id: string; name: string; collapsed: boolean }[]
  items: (
    | { type: "connection"; id: ConnectionId }
    | { type: "folder"; id: string; children: ConnectionId[] }
  )[]
}
```

Connections missing from the layout are listed after it by name; ids that no longer exist are
dropped when the frontend reconciles the layout with `connections_list`. While the saved layout is
loading the frontend makes no layout changes, so it never overwrites the file with the default
order.

## MySQL sessions

One `sqlx::MySqlPool` per connection id, created on `mysql_connect`, `test_before_acquire(true)`,
`max_connections(4)`, `acquire_timeout(10s)`.

Connection-level errors are `sqlx::Error::Io`, `PoolClosed`, server errors 2006/2013/4031 (by
error number only; a server error's message text is never inspected), and driver-side errors
(protocol, TLS) whose text says "connection reset".

An acquire timeout while all 4 connections are checked out by running work is **not** a lost
connection: the call rejects at once with `kind: "connection"` and the message "All pooled
connections are busy; wait for a running query or open another connection", is not retried
and changes no state. An acquire timeout while the pool had room (it could not open a
connection in time) counts as connection-level. Retry policy:

- A failure **before the statement is sent** (acquiring the connection, the `USE` for
  `options.database` or a replayed `USE`) is retried **once** on a fresh connection.
- A failure **while a statement runs** is retried once only for read statements: those starting
  with `SELECT`, `SHOW`, `EXPLAIN`, `DESCRIBE`, `DESC`, `WITH`, `TABLE` or `VALUES` that contain
  no `INSERT` / `UPDATE` / `DELETE` / `REPLACE` statement (e.g. `WITH ... DELETE`, `EXPLAIN
  ANALYZE UPDATE`) and no `INTO OUTFILE` / `INTO DUMPFILE`. Any other statement is not re-run
  and the call rejects with `kind: "connection"` and a message starting "The server dropped the
  connection while the statement was running; it may or may not have been applied.". The
  same rule applies to `mysql_export`.
- A retried result has `reconnected: true`; after a connection was lost without a retry, the
  next result reports `reconnected: true`.

A background task pings each pool every 30 s and emits state events. It pings an idle pooled
connection (a dead one emits `error` and the next result reports `reconnected: true`), opens one
only when the pool is empty, and skips the check without any event while every open connection
is checked out. Any successful round trip while the state is `error` or `reconnecting` emits
`connected`. `mysql_disconnect` (and `connections_delete`) remove the session and emit
`disconnected` immediately; running queries finish on their connection and the pool closes
afterwards without further state events.

`mysql_connect` for an id that is already open first closes that session (`disconnected`),
then emits `connecting` and either `connected` (new session) or `error` (no session left), so
the last event always matches whether a session exists.

Event `mysql:state` payload:

```ts
interface MysqlStateEvent {
  connectionId: ConnectionId
  state: "connecting" | "connected" | "reconnecting" | "disconnected" | "error"
  message?: string
}
```

```ts
interface MysqlSessionInfo { serverVersion: string; currentDatabase: string | null }

interface ColumnInfo {
  name: string
  typeName: string            // MySQL type name upper-cased: "INT", "VARCHAR", "DATETIME", "JSON",
                              // "TINYINT UNSIGNED", ... (see "Binary-flagged strings" below)
  table: string | null        // origin table when known
  nullable: boolean
}

// Cell values are tagged so BIGINT/DECIMAL never lose precision in JS.
type Cell =
  | { t: "null" }
  | { t: "str"; v: string }
  | { t: "int"; v: string }        // decimal string, any integer width
  | { t: "float"; v: number }
  | { t: "bool"; v: boolean }      // BIT(1), and TINYINT(1) when every value in the result is 0 or 1
                                   // (otherwise the whole TINYINT(1) column is `int`)
  | { t: "decimal"; v: string }
  | { t: "date"; v: string }       // "YYYY-MM-DD"
  | { t: "time"; v: string }       // "HH:MM:SS[.ffffff]"
  | { t: "datetime"; v: string }   // "YYYY-MM-DD HH:MM:SS[.ffffff]" (no timezone conversion)
  | { t: "json"; v: string }       // raw JSON text
  | { t: "bytes"; v: string }      // base64

type QueryResult =
  | {
      kind: "rows"
      columns: ColumnInfo[]
      rows: Cell[][]
      rowCount: number            // rows returned (after truncation)
      truncated: boolean          // true when maxRows cut the result
      elapsedMs: number
      reconnected: boolean
      statement: string           // the statement that produced this result
    }
  | {
      kind: "exec"
      affectedRows: number
      lastInsertId: string | null
      elapsedMs: number
      reconnected: boolean
      statement: string
    }

interface QueryOptions { database?: string; maxRows?: number /* default 1000 */ }
```

Binary-flagged strings: MySQL flags both real binary strings (`BINARY`, `VARBINARY`, `BLOB`
types) and text with a `_bin` collation (including `JSON_UNQUOTE` / `->>` results) as binary,
and sqlx does not expose the collation. For such columns:

1. When the statement reads a single base table (`SELECT ... FROM t [alias] [WHERE ...]`,
   `TABLE t`; no joins, unions or derived tables), `information_schema.COLUMNS.DATA_TYPE` of the
   column with the same name decides: binary types are `bytes` with the binary `typeName`,
   others `str` with the text `typeName` (`VARCHAR`, `TEXT`, `LONGTEXT`, ...). Columns are
   matched by result name, so an alias reusing another column's name can be misattributed.
2. Otherwise the values decide: if every value is valid UTF-8 the column is `str` with the text
   `typeName` (also when the column has no rows or only `NULL`s); if any value is not, every
   value of the column is `bytes` with the binary name.
   `mysql_export` streams rows and decides per value in this case.

| command | args | returns |
| --- | --- | --- |
| `mysql_connect` | `connectionId`, `secret?: string` (session-only password, see Secret storage) | `MysqlSessionInfo` |
| `mysql_disconnect` | `connectionId` | `void` |
| `mysql_query` | `connectionId`, `sql`, `options: QueryOptions` | `QueryResult[]` – one entry per statement in `sql` (split on `;` outside strings/comments by the backend; `/*! ... */` executable comments count as statements). Only a statement's first result set is returned, even when it is empty (a `CALL` returning several sets); `mysql_export` does the same. Stops at the first failing statement and rejects with `kind: "query"`; the message starts with the MySQL error text. An `options.database` (or default database) that does not exist or is not accessible rejects with `kind: "invalid_input"`. |
| `mysql_databases` | `connectionId` | `string[]` (excludes `information_schema`, `performance_schema`, `mysql`, `sys`) |
| `mysql_schema` | `connectionId`, `database` | `SchemaSnapshot` for that database |

## MySQL grid edits

The frontend accumulates edits against a result whose rows come from exactly one base table with
a primary key (determined from `SchemaSnapshot`). It sends them as a batch; the backend executes
them inside one transaction and rolls back on the first failure.

```ts
type RowChange =
  | { type: "update"; key: Record<string, Cell>; set: Record<string, Cell> }
  | { type: "delete"; key: Record<string, Cell> }
  | { type: "insert"; values: Record<string, Cell> }

interface ApplyChangesResult { affectedRows: number; elapsedMs: number }
```

| command | args | returns |
| --- | --- | --- |
| `mysql_apply_changes` | `connectionId`, `database`, `table`, `changes: RowChange[]` | `ApplyChangesResult` |

Backend rules: `database`, `table` and every column name must exist in the live schema
(re-fetched for the call) or the command rejects with `invalid_input`. The frontend sends
`database` and `table` spelled as the query wrote them (what MySQL resolved), never the cached
snapshot's spelling. The backend takes an exact match first, otherwise the only name that differs
just in letter case; several case-insensitive matches without an exact one reject with
`invalid_input`. Column names are sent as the schema spells them and resolved the same way
(MySQL column names ignore letter case, so a stale spelling still names one column); two names
for the same column reject with `invalid_input`. Identifiers are quoted with
backticks, values are always bound parameters. An `update` or `delete` whose `WHERE` matches
anything other than exactly 1 row fails the whole batch with `kind: "query"`.

## Export

```ts
type ExportFormat = "csv" | "json" | "sql"
interface ExportOptions {
  format: ExportFormat
  path: string                 // absolute path returned by the dialog plugin's save()
  tableName?: string           // for "sql" INSERT statements; default "export"
  includeHeader?: boolean      // csv, default true
  database?: string            // mysql_export only: schema to run `sql` in; default the session database
}
interface ExportResult { rows: number; bytes: number; elapsedMs: number }
```

| command | args | returns |
| --- | --- | --- |
| `mysql_export` | `connectionId`, `sql`, `options: ExportOptions` | `ExportResult` – re-runs `sql` (single statement) and streams every row to `path` without the `maxRows` cap. |
| `export_rows` | `columns: ColumnInfo[]`, `rows: Cell[][]`, `options: ExportOptions` | `ExportResult` – writes rows already in the frontend (selection or visible page). |

Paths: `export_rows`, `mysql_export` and `dynamo_export` only write to a file the user picked in
the save dialog (the dialog plugin adds it to the runtime fs scope, which the commands check);
any other path rejects with `kind: "invalid_input"` ("Choose the file through the save
dialog"). Files are written to a new temp file next to the target (owner-only, `0600` on unix)
and renamed into place; a failed export leaves no file behind.

Formatting: CSV follows RFC 4180 with UTF-8 and `\n` line ends, `null` → empty field, bytes →
base64. JSON writes an array of objects keyed by column name, numbers for `int` values that fit in
53 bits and strings otherwise, `decimal` as string, dates as strings; a repeated column name gets
the first free `_2`, `_3`, ... suffix as its key (`id`, `id_2`). SQL writes
`INSERT INTO \`table\` (...) VALUES (...);` one row per line with standard MySQL escaping.

Known limitation: CSV cells are written verbatim, so a value starting with `=`, `+`, `-` or `@`
can be interpreted as a formula by spreadsheet applications (CSV formula injection).

Known limitation (read-statement retry): a statement is classified as a read by its text only,
so a `SELECT` that calls a stored function with side effects (one that writes data) is still
re-run once after a connection loss.

Known limitation (`NO_BACKSLASH_ESCAPES`): the statement splitter, the read-statement check and
the SQL export format treat `\` inside quoted strings as an escape character, as MySQL does by
default. Sessions with `sql_mode` `NO_BACKSLASH_ESCAPES` are not supported: a string ending in
`\` can be split or classified wrongly, and exported INSERT statements need that mode off.

## Frontend stores (ownership)

- `src/state/connectionsStore.ts` – configs, dialog open state, test status. Owned by the connections feature.
- `src/state/sessionsStore.ts` – per connection: `state`, `serverVersion`, `currentDatabase`, `schema` cache. Owned by the query feature.
- `src/state/tabsStore.ts` – open tabs, active tab, per-tab sql text and last result. Owned by the query feature.
- `src/state/workspaceSync.ts` – no state of its own; mirrors the tabs store's query tabs into `workspace.json` (see Workspace). Owned by the shell.
- `src/state/queryOutputStore.ts` – the query Output log per connection, unseen-error marks and each query tab's bottom panel (Results or Output). `src/state/queryOutputSync.ts` mirrors the log into `query-output.json` (see Query output). Owned by the query feature.
- `src/state/athenaStore.ts` – per Athena connection: `databases`, `schemas` cache (same `SchemaSnapshot` shape as MySQL), `currentDatabase`, loading flags. Owned by the query feature (filled by the schema tree and the query tab); completion and the database switcher read it.

## DynamoDB

Items cross IPC in the **DynamoDB JSON wire format** (`{"S": "..."}`, `{"N": "12"}`, `{"M": {...}}`,
`{"L": [...]}`, `{"SS": [...]}` ...) so no type is lost. The frontend converts to a plain JSON view
for reading and infers types back when the user edits in plain mode; set types (`SS`, `NS`, `BS`)
can only be edited in wire mode.

```ts
type AttributeValue = Record<string, unknown>           // one wire-format attribute
type Item = Record<string, AttributeValue>

interface KeyAttribute { name: string; type: "S" | "N" | "B" }
interface KeySchema { hash: KeyAttribute; range: KeyAttribute | null }
interface IndexDescription {
  name: string
  kind: "gsi" | "lsi"
  keySchema: KeySchema
  projection: "all" | "keys_only" | "include"
}
interface TableDescription {
  name: string
  status: string                      // "ACTIVE" ...
  keySchema: KeySchema
  indexes: IndexDescription[]
  itemCount: number | null            // approximate, from DescribeTable
  sizeBytes: number | null
  billingMode: string | null
}

type RangeCondition =
  | { op: "eq" | "lt" | "le" | "gt" | "ge" | "begins_with"; value: AttributeValue }
  | { op: "between"; from: AttributeValue; to: AttributeValue }

interface QueryRequest {
  table: string
  index?: string
  hash: AttributeValue
  range?: RangeCondition
  filter?: string                     // FilterExpression using #n / :v placeholders
  names?: Record<string, string>      // ExpressionAttributeNames
  values?: Record<string, AttributeValue>
  limit?: number                      // page size, default 100, max 1000
  startKey?: Item
  scanForward?: boolean               // default true
}

interface ScanRequest {
  table: string
  index?: string
  filter?: string
  names?: Record<string, string>
  values?: Record<string, AttributeValue>
  limit?: number
  startKey?: Item
}

interface Page {
  items: Item[]
  lastKey: Item | null                // pass back as startKey for the next page
  count: number
  scannedCount: number
  elapsedMs: number
}
```

| command | args | returns |
| --- | --- | --- |
| `dynamo_list_tables` | `connectionId` | `string[]` (all pages of ListTables) |
| `dynamo_describe_table` | `connectionId`, `table` | `TableDescription` |
| `dynamo_query` | `connectionId`, `request: QueryRequest` | `Page` |
| `dynamo_scan` | `connectionId`, `request: ScanRequest` | `Page` |
| `dynamo_get_item` | `connectionId`, `table`, `key: Item` | `Item \| null` |
| `dynamo_put_item` | `connectionId`, `table`, `item: Item`, `expect: "exists" \| "not_exists" \| "any"` | `void`. `exists` adds `attribute_exists(hashKey)` (safe update), `not_exists` adds `attribute_not_exists(hashKey)` (safe create). Condition failures reject with `kind: "query"`. |
| `dynamo_delete_item` | `connectionId`, `table`, `key: Item` | `void` |
| `dynamo_update_item_attributes` | `connectionId`, `table`, `key: Item`, `changes: { name: string; value: AttributeValue; expected: AttributeValue \| null }[]` | `void`. One `UpdateItem` with `SET` for every change (names and values only as placeholders). Its condition requires the item to exist (`attribute_exists(hashKey)`) and each attribute to still equal `expected`, or to be missing when `expected` is null. A failed condition writes nothing and rejects with `kind: "query"` ("the item was changed or deleted since it was loaded ..."). Empty `changes`, a key attribute, a repeated name or a malformed value rejects with `kind: "invalid_input"`. |
| `dynamo_export` | `connectionId`, `request: { scan: ScanRequest } \| { query: QueryRequest }`, `options: { format: "json" \| "jsonl" \| "csv"; path: string }` | `ExportResult` – follows `lastKey` until exhausted. CSV flattens top-level attributes; nested values are written as JSON text. |

Known limitation (`dynamo_export` CSV): cells are written verbatim, so a value starting with `=`,
`+`, `-` or `@` can be interpreted as a formula by spreadsheet applications (CSV formula
injection).

`N` values (including `NS` members and keys/values in requests) must use DynamoDB number
syntax: optional sign, digits with an optional fraction (`5`, `5.`, `.5`), optional exponent
(`1e+21`, `1e-7`). Anything else (`""`, `abc`, `1..2`, `--1`) rejects with `kind: "invalid_input"`.

Credentials are resolved per connection through `aws-config` (profile or stored keys) once on
first use and cached. A `profile` connection uses only that `~/.aws` profile (static keys, SSO,
`credential_process`, assume-role); `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` in the
environment do not override it. The connection's `region` is always used. A `credential` error
kind means the profile is missing, expired (SSO) or rejected; the message tells the user what to
run (e.g. `aws sso login --profile <name>`). `AccessDeniedException` (IAM denied this operation
for otherwise valid credentials) is `kind: "query"` with a message starting "Access denied by
IAM for this operation:" and keeps the cached credentials.

## Settings

Persisted as JSON at `<app config dir>/settings.json`, written atomically. Unknown keys are kept so
older builds don't drop newer settings.

```ts
interface Settings {
  theme: "system" | "light" | "dark"           // default "system"

  }
```

| command | args | returns |
| --- | --- | --- |
| `settings_get` | – | `Settings` (defaults merged over the file). A `settings.json` that is not a JSON object returns the defaults (logged) and is left as is. |
| `settings_set` | `settings: Partial<Settings>` (nested groups may be partial too) | saved `Settings`. The input is deep-merged over the stored settings (objects key by key, other values replaced), so a client sends only the fields it changes. A non-object input or an out-of-range merged value → `invalid_input`. Over a corrupt `settings.json` the file is moved to `settings.json.bak` and the input is merged over the defaults. A changed `secretStore` moves the secrets (see Secret storage). |

## Workspace

The query tabs open when the app last ran, persisted as JSON at `<app config dir>/workspace.json`,
written atomically with owner-only (0600) permissions on unix. Only what a tab *is* is saved:
results, grid edits, errors and run state are not.

```ts
interface Workspace {
  version: 1
  activeTabId: string | null                    // null, or the id of one of `tabs`
  tabs: WorkspaceTab[]                          // in tab bar order; MySQL and Athena query tabs only
}
interface WorkspaceTab {
  id: string                                    // non-empty, unique in `tabs`
  kind: "query"
  connectionId: ConnectionId                    // non-empty
  engine: "mysql" | "athena"
  title: string
  sql: string
  database: string | null
}
```

| command | args | returns |
| --- | --- | --- |
| `workspace_load` | – | `Workspace \| null`. A missing file is `null`. A file that is not a version 1 workspace object is `null` too (logged to stderr) and is left as is until the next save replaces it. Tabs in the file that don't parse or repeat an id are dropped; an `activeTabId` that names no remaining tab becomes `null`. A file that exists but cannot be read rejects with `kind: "io"`. |
| `workspace_save` | `workspace: Workspace` | `void`. Replaces the file. Any type error, another `version`, an empty or repeated tab id, or an `activeTabId` that names no tab → `invalid_input` and nothing is written. |

`connections_delete` does not touch the file: the frontend closes the deleted connection's tabs,
which saves the workspace again.

Frontend (`src/state/workspaceSync.ts`, started by the shell): once the connection list has
loaded, `workspace_load` runs once and its tabs reopen in one tabs store update, dropping tabs
whose connection no longer exists or is of another kind than the tab's engine. The saved active
tab becomes active again (the first tab when it is gone), and the "Query N" counter continues
from the highest restored N. Restoring opens no MySQL session and loads no Athena catalog: a
reopened MySQL tab connects (asking for the password when none is stored) on its first run, or
when its database picker is clicked or opened with Enter, Space or Down. Focusing the picker
never connects, and after a cancelled password prompt only a new press asks again. Completion
in a reopened Athena tab makes no AWS call until that connection's catalog is used (database
picker, database switch, schema tree). Until the restore finished nothing is saved, so the empty
startup state never replaces the file; a failed `workspace_load` leaves saving off for that run.
Afterwards opening, closing or switching tabs, or changing a tab's database, saves right away (changes in the same task are merged into one save); editor text is saved
1000 ms after typing stops, or when the window closes. Saves never overlap.

Saving on close is best effort, not guaranteed. Closing the window waits up to 1.5 s for the
last save (through the window's close request, which is why the capability grants
`core:window:allow-destroy`). Quitting from the app menu (Cmd+Q) sends no close request; only
`pagehide` starts a save then, and the process may exit before it is written. Text typed in the
last second before such a quit, or before a crash, can be lost. A failed save is logged to the console once per
failure streak, without a toast.

## Query output

The Output tab of a query tab's bottom panel logs what the database returned: one entry per
executed statement, and one per run that failed as a whole or was cancelled. Only the SQL text
(cut to 10,000 UTF-16 units, never inside a surrogate pair) and a summary are kept, never row data. Persisted per connection at
`<app config dir>/query-output.json`, written atomically with owner-only (0600) permissions on
unix, for `query.outputRetentionDays` days.

```ts
interface OutputFile {
  version: 1
  connections: Record<ConnectionId, OutputEntry[]> // oldest first, at most 2000 per connection
}
interface OutputEntry {
  id: string
  connectionId: ConnectionId                    // the key it is filed under
  tabId: string                                 // query tab that ran it; may be closed
  at: number                                    // epoch ms when the run finished
  sql: string
  sqlTruncated: boolean
  elapsedMs: number | null
  outcome:
    | { kind: "rows"; rowCount: number; truncated: boolean }
    | { kind: "exec"; affectedRows: number; lastInsertId: string | null }
    | { kind: "error"; message: string }
    | { kind: "cancelled" }
}
```

The backend checks only the envelope (an object with `version: 1` whose `connections` maps
non-empty ids to arrays) and the size; the entries are the frontend's to validate.

| command | args | returns |
| --- | --- | --- |
| `query_output_load` | – | the stored JSON, or `null`. A missing file is `null`; so is one larger than 16 MiB or with another envelope, which is first moved to `query-output.json.bak` (replacing an older backup, logged to stderr) so the next save can't destroy it. A file that exists but cannot be read, or a bad file that cannot be moved aside, rejects with `kind: "io"`. |
| `query_output_save` | `output: OutputFile \| null` | `void`. Replaces the file; `null` removes it. Another envelope or a body over 16 MiB → `invalid_input` and nothing is written. |

Frontend (`src/state/queryOutputSync.ts`, started with the app shell next to the workspace sync
and kept for the life of the window): once settings and the connection list have loaded,
`query_output_load` runs once (not at all with a retention of 0). While settings failed to load
(the retention would only be the default) nothing is loaded or saved; a later successful
settings load resumes. Entries that don't parse are dropped, as are
connections that no longer exist and entries older than the retention; the result goes in front
of the entries logged meanwhile and is written back. Later changes to the log are saved 1000 ms
after the last one, and on window close (best effort, as for the workspace; one close listener
runs the workspace and output saves together and waits for both). Every save drops entries
older than the retention and, past 12 MiB encoded, the oldest entries; the log in memory drops
them too when the retention changes and, at most once a minute, when entries are added. Setting
the retention to 0 removes the file, even when the load had failed; the log then lives for the
session only. A deleted connection's
entries are dropped from the log and from the next save. A failed load leaves saving off for
that run; a failed save is logged once per failure streak.

## Secret storage

`Settings` gains `secretStore: "keychain" | "file"` (default `"keychain"`). The user chooses it in
Settings; the trade-off is spelled out there.

- `keychain`: the OS keyring, as before.
- `file`: `<app config dir>/secrets.json`, a JSON object of connection id to secret, written
  atomically with mode 0600. It is protected by file permissions only, like `~/.aws/credentials`.

The active store is read from settings on every secret operation, so switching takes effect at
once; settings that cannot be read fall back to `keychain`. Secrets are moved when possible;
ones the old store refuses to hand over stay there: when `settings_set` changes `secretStore`,
each saved connection's secret is read from the old store, written to the new one and then
removed from the old one. A connection whose secret could not be moved reports
`connections_has_secret === false` and the app asks for the password when it is opened. The
move never fails `settings_set` (failures are only logged). Deleting a connection removes its
secret from both stores.

### Session-only passwords

| command | args | change |
| --- | --- | --- |
| `mysql_connect` | `connectionId`, `secret?: string` | when `secret` is given it is used for this session only and nothing is stored |
| `connections_test` | unchanged | – |
| `dynamo_*` | – | a DynamoDB key connection without a stored secret rejects with `credential`; the app asks the user to edit the connection |

When a MySQL connection has no stored secret (`connections_has_secret` is false) the frontend
shows a password prompt before `mysql_connect`, with a "Remember password" option that saves it
through `connections_save(config, secret)`.

## SSH tunnels (MySQL)

A MySQL connection can go through an SSH bastion, like MySQL Workbench's "Standard TCP/IP over
SSH". The backend opens a local listener on `127.0.0.1:<random port>`, forwards every accepted
connection over the SSH session to `host:port` as seen from the bastion, and points the sqlx pool
at the local port. The tunnel belongs to the session: `mysql_disconnect` closes it, and the
reconnect path re-opens it when the SSH session has dropped.

```ts
interface SshConfig {
  host: string                 // bastion host or IP
  port: number                 // default 22
  user: string
  auth:
    | { type: "agent" }                        // SSH agent (SSH_AUTH_SOCK), default
    | { type: "key"; keyPath: string }          // OpenSSH private key; passphrase in the secret store
    | { type: "password" }                     // password in the secret store
}

interface MysqlConnectionConfig {
  // ...existing fields; `host`/`port` are then the MySQL address as seen from the bastion
  ssh?: SshConfig
}
```

Secrets: the MySQL password keeps the connection id as its key. The SSH password or key
passphrase is stored under `<connection id>:ssh` in the active secret store. `connections_save`
and `connections_test` take a second optional argument `sshSecret: string | null` with the same
null-keeps / empty-clears semantics as `secret`. `connections_has_secret(id, "ssh")` reports it
(second argument `which: "db" | "ssh"`, default `"db"`).

Validation (`invalid_input`): ssh host and user non-empty, port in range, keyPath absolute and
readable. `tls: "verify_identity"` is rejected together with `ssh` (sqlx connects to `127.0.0.1`
and cannot check the certificate against the real host name); use `verify_ca`. A connection id
must not end with `:ssh`.

Secret reuse: the stored database password is only reused (save with `secret: null`, test) while
the MySQL target and the bastion host/port/user (or no SSH) stay the same; the SSH auth method or
key file does not matter for it. The stored SSH secret is only reused while the bastion
host/port/user, auth type and keyPath stay the same; otherwise `invalid_input` asks for it again.
Saving a config without `ssh` (when the previous one had it) removes the SSH secret.
`connections_delete` removes both entries from both stores, and switching the secret store moves
both.

SSH auth: `password` needs the SSH secret (`ssh`: "The SSH password ... is not set" otherwise).
`key` loads the OpenSSH/PuTTY key; an unencrypted key needs no secret, an encrypted one without a
passphrase fails with kind `ssh` and a message starting with `Key passphrase required`. `agent`
tries every key of the agent at `SSH_AUTH_SOCK` (macOS and Linux only). The tunnel sends a
keepalive after 15 s without server traffic and counts the SSH session as dropped after 3
unanswered ones.

Host keys are checked against `~/.ssh/known_hosts` (read only) and the app's own
`<app config dir>/known_hosts` (mode 0600). Plain, hashed (`|1|...`), `[host]:port`, wildcard
and negated patterns and `@revoked` are understood; `@cert-authority` lines are ignored, and
`~/.ssh/config` (aliases, `HostKeyAlias`, `ProxyJump`) is not read. An unknown or changed host
key rejects with kind `ssh_host_key`. The message starts with `<keytype> SHA256:<fingerprint>`
and its last line is the known_hosts line `<host or [host]:port> <keytype> <base64>`. When the
user accepts, the frontend calls `ssh_trust_host(host, port, keyLine)` with that line, which
appends it to the app's known_hosts, and then retries. A changed (or revoked) key is never
trusted from the app: its message contains the word `changed`, `ssh_trust_host` refuses it with
`invalid_input`, and the user has to remove the old entry by hand. An unknown key's message never
contains `changed`.

`AppErrorKind` gains `"ssh_host_key"` and `"ssh"` (any other SSH failure: unreachable bastion,
authentication rejected, forward refused; the message names the step).

| command | args | returns |
| --- | --- | --- |
| `ssh_trust_host` | `host`, `port`, `keyLine` (the last line of the `ssh_host_key` message) | `void` |
| `connections_save` | `config`, `secret`, `sshSecret?` | as before |
| `connections_test` | `config`, `secret`, `sshSecret?` | as before; goes through the tunnel |
| `connections_has_secret` | `id`, `which?: "db" \| "ssh"` | `boolean` |

`mysql:state` events are unchanged. When the SSH session dropped, the next query or the 30 s
health check re-opens the tunnel on a new local port with a new pool (`reconnecting`, then
`connected`; the first result reports `reconnected: true`). A tunnel failure during reconnect
surfaces as `error` with the SSH message, and the call fails with kind `ssh` / `ssh_host_key`.

The password prompt flow applies to the SSH secret too: when the SSH auth needs a secret that is
not stored, `mysql_connect` accepts `sshSecret?: string` for the session only
(`mysql_connect(connectionId, secret?, sshSecret?)`); it is kept in memory to re-open the tunnel.

## Athena

Amazon Athena runs each statement as an asynchronous *query execution*: the backend starts it,
the frontend waits for it (and may cancel it), and the rows are read from Athena's result API.
There is no session or connection state to keep: like DynamoDB, one SDK client per connection id
is built on first use from the saved config and dropped on `connections_delete`, on edit, or after
a `credential` error (so `aws sso login` is picked up on the next call). A `keys` connection whose
secret is missing from the active secret store rejects with `kind: "credential"`.

Every statement **costs money** (billed by bytes scanned), so nothing is ever re-run
automatically: there is no retry and no `reconnected` flag.

**Output location** (where Athena writes result files) is resolved on every client build and
on `connections_test`, in this order:

0. a workgroup with *managed query results* needs no location: `StartQueryExecution` is sent
   without one and `connections_test` reports `outputLocation: null`, `missingBucket: null`;
1. the workgroup's own `ResultConfiguration.OutputLocation` when the workgroup *enforces* its
   configuration;
2. `config.outputLocation` when set;
3. the workgroup's `OutputLocation` when set;
4. the console's default bucket `s3://aws-athena-query-results-<account id>-<region>/`, with
   the account id from `sts:GetCallerIdentity`. `HeadBucket` is sent with
   `x-amz-expected-bucket-owner` set to that account, so only a bucket the account owns counts
   as existing; a 404 or 403 (missing, or owned by someone else, since the name is global and
   can be squatted) means nothing is created: `connections_test` reports it in `missingBucket` and `athena_start`
   rejects with `kind: "invalid_input"` naming the bucket (`athena_databases` / `athena_schema`
   need no location and still work; the check runs again on the next `athena_start`, so a bucket
   created elsewhere is picked up). Any other `HeadBucket` failure is reported as is.

```ts
interface AthenaTestInfo {
  workgroup: string               // the workgroup probed ("primary" when the config has none)
  outputLocation: string | null   // resolved as above; null with managed results or when missingBucket is set
  missingBucket: string | null    // default bucket name that would have to be created
}

interface AthenaQueryOptions {
  database?: string               // QueryExecutionContext.Database; absent = no default database
  catalog?: string                // QueryExecutionContext.Catalog; absent = "AwsDataCatalog"
  maxRows?: number                // rows kept, default 1000 (same meaning as mysql_query)
}

interface AthenaStats {
  executionId: string
  dataScannedBytes: number        // Statistics.DataScannedInBytes (0 for metadata statements)
  engineMs: number | null         // Statistics.EngineExecutionTimeInMillis
  outputLocation: string | null   // ResultConfiguration.OutputLocation of the execution
}

// A RowsResult (same `columns` / `rows` / `Cell` shapes as mysql_query) plus Athena statistics.
// `reconnected` is always false; `elapsedMs` is wall time from start to the last result page.
interface AthenaRowsResult extends RowsResult { athena: AthenaStats }
```

| command | args | returns |
| --- | --- | --- |
| `athena_workgroups` | `config: AthenaConnectionConfig`, `secret: string \| null` | `string[]` workgroup names sorted, `ListWorkGroups` across all pages. The secret fallback rule is that of `connections_test`. |
| `athena_create_output_bucket` | `config`, `secret`, `bucket: string` | `{ outputLocation: string }` (`s3://<bucket>/`). Creates the bucket in `config.region` (`LocationConstraint` except for `us-east-1`) and blocks all public access on it. Only called after the user confirmed the creation in the connection dialog. `bucket` must be the name `connections_test` reported in `missingBucket`; another name rejects with `invalid_input`. A bucket that already exists and is owned by the account counts as created. Drops the cached client so the next `athena_start` re-resolves the location. |
| `athena_databases` | `connectionId` | `string[]` sorted, `ListDatabases` of catalog `AwsDataCatalog` across all pages. |
| `athena_schema` | `connectionId`, `database` | `SchemaSnapshot` (`mysql_schema` shape) from `ListTableMetadata` across all pages. `kind` is `"view"` for `TableType` `VIRTUAL_VIEW`, else `"table"`. Columns are the table's columns followed by its partition keys; `typeName` is the Athena/Glue type as returned (e.g. `varchar`, `bigint`, `array<string>`), `nullable` true, `isPrimary` / `isAutoIncrement` false, `defaultValue` null, `comment` from the column comment. An unknown database rejects with `not_found` (Athena's `MetadataException`). |
| `athena_start` | `connectionId`, `sql: string`, `options: AthenaQueryOptions` | `{ executionId: string }` from `StartQueryExecution` in the config's workgroup with the resolved output location. `sql` is **one** statement (Athena rejects several); the frontend splits scripts and runs statements one after another. An empty statement rejects with `invalid_input`. |
| `athena_wait` | `connectionId`, `executionId`, `maxRows?: number` | `AthenaRowsResult`. Polls `GetQueryExecution` (0.5 s, growing to 2 s) until the state is terminal, then pages through `GetQueryResults` (1000 per page) until `maxRows` rows are kept; `truncated` is true when more existed. `FAILED` rejects with `kind: "query"` and `AthenaError.ErrorMessage` (else `StateChangeReason`); `CANCELLED` rejects with `kind: "query"` and the message "The query was cancelled". The first result row is dropped when it repeats the column names (Athena returns a header row for `SELECT`-like statements only). Metadata statements (`SHOW ...`, DDL) return their text rows as `str` cells; a statement with no result set returns `columns: []`, `rows: []`. |
| `athena_cancel` | `connectionId`, `executionId` | `void`. `StopQueryExecution`; already finished executions are a no-op. Once stopped, the execution is no longer tracked for the stop on delete or edit below. |

When `maxRows` rows are kept and Athena still reports a next page, one more page of one row is read and `truncated` is set only when it holds a row.

`athena_start` and `athena_wait` are two calls so a running statement can be cancelled: the tab
keeps the `executionId` while it runs.

Frontend rules for Athena tabs: a script is split on `;` outside `'…'` strings, `"…"`
identifiers (`""` escapes a quote; a backslash does not escape) and comments, and each statement
goes to `athena_start` on its own. Statements that write to S3 or the Glue catalog (`CREATE TABLE
… AS`, `CREATE [OR REPLACE] VIEW`, `INSERT`, `MERGE`, `UNLOAD`, `MSCK REPAIR`, `OPTIMIZE`, `VACUUM`) go
through the same confirmation as `DROP` / `ALTER`.
The default `LIMIT` is not added to a `SELECT` with a top-level `FETCH FIRST|NEXT … ROWS ONLY`.
`athena_workgroups` with access keys is called only once the secret field loses focus (or with a
stored secret that may be reused), never with a half-typed secret.

**Cells**: Athena returns every value as text with a column type; `athena_wait` maps them to
`Cell` by the column's type (case-insensitive, parameters ignored, e.g. `decimal(10,2)` →
`decimal`). A missing `VarCharValue` is `null`. `boolean` → `bool`; `tinyint` / `smallint` /
`integer` / `int` / `bigint` → `int` (an optional leading `-` and digits; anything else, a leading `+`
included, stays `str`); `real` / `float` / `double` → `float` (`NaN`, `Infinity`
and anything that is not a finite number stay `str`); `decimal` → `decimal`; `date` → `date`;
`time` → `time`; `timestamp` (with or without time zone) → `datetime`; `json` → `json`;
`varbinary` → `bytes` (Athena prints bytes as space-separated hex pairs, decoded to base64; each pair
must be exactly two hex digits, otherwise the value stays `str`); every other type (`varchar`, `char`, `string`, `array<…>`,
`map<…>`, `row(…)`, `interval …`, `ipaddress`, `uuid`, unknown) → `str`. `ColumnInfo.typeName`
is the Athena type upper-cased and cut at the first `(` or `<` (`VARCHAR`, `BIGINT`, `DECIMAL`,
`ARRAY`, `TIMESTAMP WITH TIME ZONE`),
`table` is null and `nullable` is false only for `Nullable` `NOT_NULL`.

**Errors** map like DynamoDB: missing or expired credentials (the DynamoDB credential codes plus
`InvalidAccessKeyId`) are `credential` and drop the cached client; `AccessDeniedException` is
`query` with a message starting "Access denied by IAM for this operation:" (the client is kept);
throttling, service and HTTP failures are `connection`; `InvalidRequestException` is
`invalid_input`; `MetadataException` / `ResourceNotFoundException` are `not_found`; anything else
is `query`.

`connections_delete` (and saving an edit of) an Athena connection drops its client and sends
`StopQueryExecution` for every execution the client started and has not yet waited to the end
(best effort, failures are only logged and the command does not wait for them), so a deleted
connection does not keep scanning. Dropping the client after a `credential` error or after
`athena_create_output_bucket` stops nothing. The frontend
also marks the running Athena tabs of a connection as cancelled when its config is saved (without
an `athena_cancel`, which would go through a client built from the new settings), so a script's
remaining statements never start under the new region or workgroup.
